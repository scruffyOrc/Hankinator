# Touch UI and motion-controller integration contract

## Decision

Use **one Pico 2 W** for the next integrated HankWinder firmware. The LVGL/touchscreen code and the existing motion controller should communicate through an in-process, display-independent controller API. Do not add an ESP32 screen controller yet.

This is a reversible decision. The API described below deliberately has no LVGL, TFT, encoder, or Mini12864 types, so the same command/snapshot contract can later cross a serial link to an ESP32 if the measured integrated build proves it necessary.

### Why one Pico first

- The production Pico 2 W build currently uses 214,312 of 524,288 bytes of RAM (40.9%) and 628,072 of 3,403,776 bytes of application flash (18.5%).
- The isolated touch build currently uses 177,948 bytes of RAM (33.9%) and 634,692 bytes of application flash (18.6%).
- Their simple RAM sum is about 392 KB (75%). That is tight enough to require measurement after integration, but it is not evidence that a second processor is required. The final combined binary will share Arduino/Pico runtime portions, while LVGL widgets and draw buffers must remain bounded.
- The production STEP train is already generated by a hardware alarm. The display must never generate steps or run in its callback. A bounded, low-priority display service can coexist with it.
- An ESP32 display adds a second firmware image, boot-order and update coordination, a communications failure mode, and a protocol that must be versioned. It does not replace the need for a direct, hard-wired STOP input on the Pico.

The strongest objection is not flash size; it is latency while SPI flushes LVGL regions and while the radio/load-cell/TMC work is active. We will address that with incremental rendering, a capped display cadence, and a measured stress test before declaring the one-Pico path production-ready.

### Current diagnostic integration target

`rpipico2w_touch_diagnostics` is the first production touch target. It runs
the complete live controller and presents only **Load cell diagnostics** and
**Weight diagnostics** through `Machine::diagnostics()`. It is deliberately
observation-only: it cannot start commissioning or winding, and it does not
offer touch tare yet. This keeps the first display integration reversible and
leaves the normal `rpipico2w` Mini12864 build operational.

It uses the proof-panel wiring: ILI9488 display on GP16--GP20, XPT2046 CS on
GP13, IRQ on GP11, and its SPI1 bus on GP12/GP14/GP15. Those pins overlap the
legacy panel, encoder, and RGB wiring, so that path is disabled only in this
target. Touch calibration is stored separately at EEPROM offset 512 and does
not alter the persistent machine-settings record at offset 0.

## Non-negotiable ownership rules

| Owner | Owns | Must not do |
|---|---|---|
| Motion/controller service | STEP hardware alarm, motor enable/DIR, Hall, TMC UART polling, HX711 reads, tare, commissioning, stall recovery, persistence, STOP safety | Call LVGL/TFT APIs or wait for touch/display work |
| Touch UI service | Page construction, touch input, button feedback, value formatting, incremental invalidation | Directly change `uiState`, `settings`, motor GPIO, alarms, or load-cell state |
| Integration façade | Validates a UI command, changes controller state, produces read-only snapshots and discrete events | Draw pixels or block on I/O |

Physical STOP remains wired directly to the Pico and is processed by the controller even if the UI is stalled, rebooting, disconnected, or displaying a stale page. Touch Pause/Resume is convenience control, not the safety control.

The forthcoming physical STOP is **stop-only**. It is not a Back/navigation control in the touchscreen product. Navigation remains a touch-screen responsibility; STOP is reserved for controller-defined run interruption.

## The façade to add

Create `include/machine_interface.h` and `src/machine_interface.cpp` in the motion-firmware fork. The names below are a contract, not a demand to copy every current global into a new type.

```cpp
namespace Machine {

enum class Mode : uint8_t { Turninator, AutoHankWinder, LoadCellFault };
enum class PageState : uint8_t {
  Booting, ModeSelect, TurnSelect, WeightSelect, HallSeek, Taring,
  LoadYarn, Winding, Pausing, Paused, Recovering, Complete, Fault,
  Commissioning, Diagnostics, Updating
};
enum class Result : uint8_t { Accepted, Busy, Invalid, Unsafe, Unsupported };
enum class FinishReason : uint8_t { Complete, UserStop, StallAbort, HallFault,
  LoadCellFault, TareFailed, DriverFault };

struct SettingsView {
  uint16_t runCurrentMa, holdCurrentMa, countTurns;
  uint16_t targetCentiGrams[3];
  bool clockwise, hallEnabled, bluetoothEnabled;
  bool commissioningValid;
  bool wifiProvisioned;
};

struct LiveView {
  Mode mode;
  PageState state;
  bool motionActive, motorEnergized, pauseAllowed, resumeAllowed, stopAllowed;
  uint16_t selectedTurns, completedTurns, targetTurns;
  uint16_t progressPermille;
  float commandedMotorRps;
  float displayedWeightGrams;
  bool weightValid;
  uint8_t healthyLoadCellMask, detectedLoadCells, requiredLoadCells;
  uint16_t sgResult;
  uint32_t driverStatus;
  uint8_t hallState;
  uint8_t stallIncidents;
  bool countUncertain;
  uint8_t commissioningState, commissioningReference, commissioningLeg;
  uint8_t commissioningSamples, commissioningSamplesRequired;
  char message[64];
};

struct Event {
  enum class Type : uint8_t { StateChanged, Fault, TareComplete,
    RunComplete, PairingChanged, CommissioningComplete, ResetComplete } type;
  uint32_t sequence;
  FinishReason finishReason;
  char message[64];
};

void begin();
void service();                       // Called from App::loop; never blocks.
const LiveView& view();               // Coherent, copied-on-update snapshot.
bool nextEvent(Event& event);         // Fixed-size event queue; no heap use.

Result selectCountTurns(uint16_t turns);
Result selectWeightProgram(uint8_t program); // 0 Mini, 1 Half, 2 Full
Result startSelectedRun();
Result pause();
Result resume();
Result stop();                        // Same semantics as physical STOP.

Result setRunCurrent(uint16_t ma);
Result setHoldCurrent(uint16_t ma);
Result setClockwise(bool clockwise);
Result setHallEnabled(bool enabled);
Result setWeightTarget(uint8_t program, uint16_t centiGrams);
Result setBluetoothEnabled(bool enabled);
Result openPairingWindow();
Result closePairingWindow();
Result startCommissioning();
Result confirmCommissioningStep();
Result cancelCommissioning();
Result startWeightDiagnosticsTare();
Result factoryReset(bool eraseCommissioning);

}
```

The façade owns persistence. Each valid setting command applies the setting, validates it, persists it, and refreshes `SettingsView`; the UI never saves settings itself. Commands that are unsafe in the current state return `Busy` or `Unsafe` without changing state.

`LiveView` is intentionally a snapshot rather than a collection of getters. It prevents the renderer from combining a turn count from one controller iteration with a weight or fault state from another. Use a small critical section or a sequence-counter copy if a snapshot can be written by more than one context.

## Screen-to-controller map

| Touch UI screen | Commands required | Data/events required |
|---|---|---|
| Home | none | product mode, commissioning-valid state, boot/fault state |
| Turn count | `selectCountTurns`, `startSelectedRun` | saved/default count, min/max, mode availability |
| Weight program | `selectWeightProgram`, `startSelectedRun` | Mini/Half/Full targets and weight-capability availability |
| Tare / Load Yarn | `startSelectedRun` begins Hall seek/tare; a separate `confirmLoadYarn` may be added if needed | Hall seek progress, tare status, clear operator prompt, tare failure reason |
| Winding gauge | `pause`, `resume`, `stop` | progress, turns, commanded speed, phase, pause/recovery state, live weight when valid, uncertainty/fault reason |
| Completion | none initially; later `repeatLastRun` | final turns, final settled weight, valid/invalid flag, finish reason |
| Weight targets | `setWeightTarget` | the three persisted target values and min/max |
| Motor current | `setRunCurrent`, `setHoldCurrent` | applied values, allowed ranges, driver availability/fault |
| Rotation direction | `setClockwise` | persisted direction |
| Hall feedback | `setHallEnabled` | persisted state and live Hall state |
| Commissioning | `startCommissioning`, `confirmCommissioningStep`, `cancelCommissioning` | existing `Commissioning` state, message, reference mass, leg, samples, validation values, complete/failure event |
| Load-cell diagnostics | none | raw channels, healthy mask/status, timing delay, suspicious/missing masks, timeout/jump counters |
| Weight diagnostics | `startWeightDiagnosticsTare` | tare status, current settled/derived weight, channel quality |
| Connectivity | `setBluetoothEnabled`, `openPairingWindow`, `closePairingWindow` | enabled, pairing-open, seconds remaining, connected state |
| Factory Reset | `factoryReset(eraseCommissioning)` after UI authorization | accepted/failed and `ResetComplete` event; then controller reboots |

## Important semantic choices before implementation

1. **Start means “begin the controller-owned sequence,” not “turn immediately.”** For an Auto HankWinder run, `startSelectedRun()` may enter Hall seek, energized stationary tare, and Load Yarn before it enters Winding. The touchscreen follows the resulting `PageState`; it must not invent a fixed timer.
2. **STOP has one controller implementation.** Touch STOP and physical STOP call the same controller operation. The existing behavior remains: moving run = de-energized coast/abort; paused count run = successful final measurement; all safety/fault cases stay controller-defined.
3. **Pause/Resume applies only when the snapshot says it is allowed.** The UI should disable or ignore its round button during an automatic measurement boundary, final-settle window, hall fault, or other recovery phase.
4. **Diagnostics is read-only except TARE.** The removed timing-tuning screen stays removed from normal UI. Raw evidence remains available to the diagnostics page and Bluetooth logs.
5. **Factory reset cannot simply call the current `loadFactoryDefaults()`.** That function always clears commissioning validity. Implement `factoryReset(bool eraseCommissioning)` so the `false` path resets user settings while retaining the calibration coefficients, collar masses, and `loadCellCalibrationValid`; the `true` path clears those as well. Both paths must clear saved Wi-Fi credentials and Bluetooth bonds, persist once, and reboot.
6. **Touch authorization is only guardrail UX.** The commissioning reset code protects against accidental taps, not against an attacker with firmware access. It should not be treated as security.

## Implementation sequence for the motion-firmware fork

1. Fork the current production firmware before replacing the Mini12864 UI. Keep the timer-driven motion, Hall, TMC, load-cell, commissioning, Bluetooth, Wi-Fi updater, telemetry, and current physical STOP behavior intact.
2. Add the façade as a thin adapter over existing functions first. Do not rewrite the motion state machine. For example, `Machine::pause()` initially calls `requestPause()` after validating `uiState` and `pauseState`.
3. Add `LiveView` population once per `App::loop` iteration after motion/load-cell/TMC service. Add a fixed eight-entry event queue for transitions/faults, not a stream of display redraw requests.
4. Move setting mutations currently in `controls.cpp` behind façade setters. Preserve the existing bounds and immediate driver-current application.
5. Implement `factoryReset(bool)` correctly, including Bluetooth-bond deletion and optional commissioning retention, before exposing the touchscreen reset page to production.
6. Add the TFT/LVGL service after the controller service in the main loop. Cap normal UI rendering to 20 Hz, redraw only invalidated regions, and do not render from the hardware-alarm callback.
7. Bind the existing touch pages to commands/snapshots one screen at a time: Home/selection, preparation/winding, then settings and diagnostics. Physical STOP stays enabled throughout the migration.
8. Run a motion stress test: 4 RPS, repeated pause/resume, intentional bind/recovery, Hall correction, Bluetooth streaming, active diagnostics, and a full weight run while measuring step timing and missed Hall intervals. This is the decision gate for staying with one Pico.

## Performance guardrails and decision gate

- Keep the existing 40-row draw buffer; do not add a full 480×320 framebuffer.
- No dynamic page creation while winding except controlled transitions; preallocation can be considered later only if measured heap fragmentation appears.
- Service LVGL after `TmcDriver::poll`, `HallSensor::service`, `LoadCells::service`, safety buttons, and `updateMotor` in the main loop.
- Do not hold interrupts off for a TFT transfer.
- During winding, limit display refresh to 10–20 Hz and update only numbers/gauge regions. A static settings page may render freely while idle.
- Track free heap/high-water mark and timing jitter in a diagnostic build. Reject the one-Pico path if any of these occur: missed STEP timing, Hall false faults attributable to UI load, stale driver data caused by rendering, allocator instability, or insufficient memory margin under the stress test.

## When an ESP32 display becomes justified

Move the UI to an ESP32 only if the integrated stress test fails the guardrails, or if the final UI requires full-screen animation, large images, complex fonts, dashboards, or network/app features that materially exceed the Pico's bounded UI budget. Resistive-touch responsiveness by itself is not sufficient evidence: it is dominated by the XPT2046 panel/controller and calibration/filtering, not necessarily by Pico compute.

If that happens, use a framed, CRC-protected **UART** protocol as the first choice rather than I2C: it is easier to recover from UI resets or a disconnected cable, supports explicit message framing/versioning, and avoids making the UI a bus master that can hold the controller's shared bus. The Pico remains the safety and motion authority; the ESP32 can reboot without stopping the physical STOP path or corrupting a run.
